# The run directory and the vault

In protected mode the agent never holds validation or test data. If it did, it could score itself on validation as often as it liked and the Ladder would be decoration. So the data is split once, on disk, before anything runs.

On the two-hour synthetic file the test suite builds:

```console
$ blinded init brief.yaml --run-dir ~/runs/syn-1
workspace /Users/you/runs/syn-1/workspace
vault     /Users/you/runs/syn-1/vault
train  2024-11-28T02:00:00.100000+00:00 to 2024-11-28T03:00:00+00:00     79,116 rows  3894156e8fa7
val    2024-11-28T03:05:00+00:00 to 2024-11-28T03:30:00+00:00     39,794 rows  853028363b49
test   2024-11-28T03:35:00+00:00 to 2024-11-28T04:00:00+00:00     39,723 rows  47aff8adc62d
```

The last column is the start of each segment file's SHA-256. The run directory looks like this:

```text
syn-1/
  workspace/                 the agent's working directory
    brief.yaml               data.path: data/train.parquet, the split windows pinned
    data/train.parquet       the training rows, nothing later
    DATA.md                  clock diagnostics on train, plus the split boundaries
    RULES.md                 the contract and what the judge checks
    ARCHETYPES.md            with an archetypes brief: what runs on this data, and why not
    LEDGER.md                every trial so far, regenerated by the judge
    features/  strategies/   the agent's code
    .judge/inbox/  .judge/outbox/   file-drop requests and responses
  vault/                     the judge's; the agent cannot read it
    brief.yaml               the same brief, pointing at the vault's train copy
    train.parquet  val.parquet  test.parquet
    {train,val,test}.touch.parquet   with data.touch: the fill engine's stream, cut alike
    manifest.json            split boundaries and SHA-256 hashes
    menu.json                with an archetypes brief: the verdict on every archetype
    ledger.sqlite            every evaluation
    trials/                  the code of every trial, by hash
  agent/                     the agent's sandbox settings and hook; see {doc}`sandbox`
```

## How the rows are cut

The windows come from the brief as described in {doc}`splits`. A row goes to train if its timestamp is before the end of train, to `val.parquet` if it is before the end of validation, and to `test.parquet` otherwise. The embargo rows travel with the segment after them, because the warm validation panel needs them and the agent must not see them. Inside each file the rows keep their original order, so ties at one timestamp still resolve in file order, last wins.

`manifest.json` records the split boundaries, the embargo, the row count and SHA-256 of each segment file and of the source file, and the source file's name. It never records a row, and it does not record where the source file lives. The workspace copy of `train.parquet` is byte for byte the vault's, so the agent's local scores and the judge's train scores are computed from the same bytes.

Both briefs carry the windows as fixed boundaries under `splits.windows`, because the workspace's data ends where train ends: without the pinned windows, a local `--window train` would mean the first half of the training file.

## Touch and depth files

A market-making file keeps its book thinned to the stamps the panel reads, and puts every top-of-book row in a second file, the touch stream, that only the fill engine reads (`data.touch`: its path, tick and instrument). An arbitrage file adds the hedge venue's depth snapshots (`data.depth`), which only the hedge leg reads. `blinded init` cuts each at the segments' ends exactly as it cuts the data, so the vault holds `train.touch.parquet`, `val.touch.parquet` and `test.touch.parquet` (and the same for `depth`), each hashed in `manifest.json` under `touch` and `depth`; the workspace gets train's as `data/train.touch.parquet`, and its brief points there. The hook and the OS rules deny `val.touch.parquet` and `test.depth.parquet` as they deny `val.parquet`.

Before anything is written, init refuses a touch file whose stamps go backwards, whose prices are not whole ticks or not two-sided, or whose touch at any stamp of the data file's book rows of its instrument differs from those rows' bid, ask and sizes ({func}`~blinded.vault.check_touch`); and a depth file that lacks a level it declares ({func}`~blinded.vault.check_depth`). The judge's engine reads the touch through the panel: {meth}`RunDir.panel <blinded.vault.RunDir.panel>` attaches the vault's touch files from train to the segment it builds, and a pass on a window reads only the rows from the last one at or before the window's first decision to five minutes after its end ({class}`~blinded.sim_maker.TouchSource`). On a thinned file market making quotes only the touch file's instrument; the other books are the lattice's.

A brief with `data.theo` (a coin, its legs, an anchor) gets the theo at init ({mod}`blinded.theo`): the parameters fitted on train's rows only, the whole file filtered once with them, and the output cut at the segments' ends as the data is, `train.theo.parquet`, `val.theo.parquet` and `test.theo.parquet`, hashed under `theo` in the manifest, with `vault/theo.json` holding the parameters, the fit (its window's end, the conflation, the likelihood and the evaluations) and the innovation report of each segment. The workspace gets train's output as `data/train.theo.parquet` (a naive run the whole file's), its brief points there, and the panel reads it as the instrument `THEO.<coin>`, available when its legs' book rows are. The hook and the OS rules deny `val.theo.parquet`, `test.theo.parquet` and `theo.json`.

## Warm panels

The judge builds validation's panel from `train.parquet` and `val.parquet` together, and test's from all three, so every rolling window is warm at the first scored point. Because the segments are a partition of the rows in file order, the warm validation panel is exactly the first rows of the panel built from the whole file. The test suite checks this frame for frame.

Before it scores anything, the daemon checks each segment against its hash in the manifest.

## Refusals

`blinded init` refuses when

- the data file is inside a git work tree that does not ignore it,
- the run directory would be inside a git work tree, ignored or not, or
- the run directory exists and is not empty.

The first two say which repository and why: a run directory holds market data, and anything a work tree tracks is one `git add` away from a commit. A data file that its repository ignores is allowed, because `init` only reads it; `git check-ignore` decides, and if git is not installed the file is refused. The run directory gets no such allowance, since `init` writes the segments there and an ignore rule is easy to lose. Move the file, or choose a run directory elsewhere. The check walks up from the resolved path looking for `.git`, so a symlink from outside a repository to a file inside one is judged by that repository.
